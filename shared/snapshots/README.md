# 스냅샷 번들

**B(민서)와 C(민재)의 실행 스크립트는 `sample/` 폴더와 똑같은 형태의 결과를 만들어야 합니다.**
필드 이름 · 구조 · 타입이 하나라도 다르면 프론트가 읽지 못합니다.

형식 정의는 `shared/types/snapshot.ts`에 있습니다.

---

## 스스로 확인하는 방법

A(서진)에게 물어보지 마시고 이 명령으로 확인하세요. 통과하면 맞는 겁니다.

```bash
pnpm verify:bundle shared/snapshots/sample
pnpm verify:bundle shared/snapshots/run-20260925
```

아직 `pnpm install` 을 안 했다면 이렇게도 됩니다. 설치 없이 바로 돕니다 (Node 22.6 이상).

```bash
node --experimental-strip-types scripts/verify-bundle.ts shared/snapshots/sample
```

검증 항목:

- 12개 시점이 모두 있는가
- `runId`가 전부 같은가
- 필수 필드가 다 있는가
- 각 시점의 LP 평가액 · 미상환 · 준비금 · 누적건수 · 손실률이 **기준값과 일치하는가**

마지막 항목이 인수 조건입니다. 실제 실행 결과가 기준값과 다르면 컨트랙트나 어댑터에 버그가 있다는 뜻입니다.

---

## 폴더

```
sample/            A(서진)이 만든 기준 번들. 값은 목업 v21 실측값
run-<날짜>/         실제 테스트넷 실행 결과. B(민서)가 생성
```

프론트는 폴더만 바꿔 끼우면 됩니다.

---

## 규칙

**스냅샷은 델타가 아니라 그 시점의 전체 상태입니다.**
시점을 클릭하면 이전 상태에 변화를 더하는 것이 아니라 상태를 통째로 교체합니다.
그래서 순서를 건너뛰어도 결과가 같습니다.

**12개 스냅샷은 한 회차의 연속 실행(`t0` → `t9b`)에서 전부 생성합니다.**
일부만 재생성하는 것은 금지입니다. 시점 5를 고치면 6~9b를 전부 다시 떠야 합니다.

**모든 스냅샷의 `runId`가 같아야 합니다.**
프론트는 `runId`가 섞이면 로드를 거부합니다.

**손으로 고치지 마세요.** 스크립트 출력만 커밋합니다.

---

## 금액 단위

| 위치 | 단위 |
|---|---|
| 카드사 DB | 소수점 2자리 (`1000.00`) |
| 온체인 | 6자리 정수 (`1000000000`) |
| **스냅샷 JSON** | **USDC 단위 숫자 (`1000`)** |
| 화면 표시 | USD, 소수점 0~2자리 |

변환은 어댑터에서 한 번만 합니다.

---

## 시점 목록

| ID | seq | 내용 |
|---|---|---|
| `t0` | 0 | 사용자 앱 환불 체험 |
| `t1` | 1 | 1년 정상 운영 |
| `t2` | 2 | 최종 손실 → 워터폴 |
| `t3` | 3 | 상관 손실 → 상한 발동 |
| `t3b` | 4 | 회수 정산 |
| `t4` | 5 | LP 출금 · 유동성 |
| `t5` | 6 | 지연 후 정상 상환 |
| `t6` | 7 | 외부 운용처 동결 |
| `t7` | 8 | 체인 성공 · DB 실패 |
| `t8` | 9 | 부정 요청 거절 |
| `t9` | 10 | 발급사가 늘어날 때 |
| `t9b` | 11 | 자본이 몰려올 때 |

`t0`은 선택이 아니라 **선행 조건**입니다. 사용자 앱의 예약 취소가 `REF-2026-001`을 실제로 선지급하고 상환하며, 시점 7과 8이 이 키를 참조합니다.
