## 브랜치 규칙

브랜치는 버전이 아니라 **시간순으로 이어지는 작업 구간**입니다. 각 브랜치는 「지금까지의 develop + 이번 주제」이고, 하루 끝에 머지해야 다음 브랜치가 앞 작업을 물려받습니다.

```
develop   ──●──────●──────●──────●──────●──▶
             \    /  \   /  \   /  \   /
              ●──●    ●─●    ●─●    ●─●
            shell  timepoint user-app dashboards
```

**하루 시작**

```bash
git checkout develop
git pull origin develop
git checkout -b feat/front-<주제>
```

**하루 끝**

```bash
git push -u origin feat/front-<주제>
# GitHub에서 develop으로 PR → 셀프 머지 → 팀에 한 줄 알림
```

`develop`에 직접 커밋하지 않습니다. 내가 만든 규칙을 내가 먼저 지켜야 팀원도 따릅니다.

#### 디자인을 다듬으려면 오늘입니다

별도 단계로 두지 마세요. 어차피 오늘 `styles.css`를 만지고 있고, 나중에 하면 이미 만든 5개 화면을 다시 돌아다녀야 합니다. 예비일이 9/27 하루뿐이라 「나중에 몰아서」는 사실상 불가능합니다.

**오늘 정할 것** — `:root` 변수 몇 개라 전 화면에 한 번에 반영됩니다.

- 폰트
- 주색과 배경색 (`--violet` · `--ground`)
- 간격 스케일
- 그림자 (`--shadow-m`)

셸만 있어도 정할 수 있습니다. 색과 폰트가 어울리는지는 글자 몇 개로도 보입니다.

**화면 만들 때 정할 것** — 카드 여백, 표 밀도, 칩 크기. 실제 영문이 들어간 뒤에야 판단됩니다. 빈 박스나 Lorem ipsum으로 맞추면 텍스트를 넣는 순간 깨집니다.

**건드리지 말 것** — 무엇을 어디에 두느냐. 목업의 정보 구조는 심사위원이 이해하도록 여러 번 다듬은 결과입니다. 여백 · 정렬 · 밀도 수준에서만 손보세요.

**작업 방법**

```
1. 목업 그대로 이식해서 동작시킨다        ← 기준선
2. 한 화면(공개 뷰)에서만 색을 바꿔본다
3. 나아졌으면 :root 변수로 승격           ← 전 화면 자동 반영
4. 화면별로 미세 조정
```

전 화면을 동시에 만지면 뭐가 좋아졌는지 판단이 안 됩니다. 백지에서 상상하는 것보다 얹어놓고 보는 게 훨씬 정확합니다.

**색을 컴포넌트에 직접 박지 마세요.** 지금 `App.tsx`는 인라인에 `#6D4AFF`가 박혀 있습니다(골격 확인용). 이식하실 때 CSS 클래스로 옮기세요. 그래야 나중에 변수 하나로 전 화면을 바꿀 수 있습니다.

디자인을 크게 바꾸실 생각이라면 **오늘 결정하셔야 합니다.** 9/25에 다시 생각하면 그때는 못 돌립니다.

## 잊지 말 것

**열람 진행도는 스냅샷 바깥에 둡니다.** 스냅샷은 사전 생성된 고정 파일이라 진행도를 담을 수 없고, 상태 교체로 사라지면 안 되는 값입니다.

**시점 선택은 상태를 교체합니다.** 이전 상태에 변화를 더하는 게 아닙니다. 이게 깨지면 순서를 건너뛸 때 수치가 어긋납니다.

**목업 CSS를 그대로 옮깁니다.** Tailwind로 다시 짜지 않고, 차트도 인라인 SVG라 라이브러리가 필요 없습니다.

**레이아웃은 영문 기준으로 잡습니다.** 같은 내용이 영어로 30~50% 길어집니다.
