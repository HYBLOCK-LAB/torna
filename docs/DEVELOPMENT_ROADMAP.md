## 1. 수요일에 무엇까지 끝내는가

민서의 완료 조건은 PRD 12장에 적힌 다음 세 가지다.

1. Foundry 테스트가 전부 통과한다.
2. 로컬 anvil에서 t0부터 t9b까지 12개 시점을 연속 실행하여 스냅샷 12개를 생성한다.
3. 생성 번들이 `pnpm verify:bundle`을 통과한다. 여기에는 민재가 생성하는 라벨 파일도 필요하다.

이를 위해 Solidity뿐 아니라 **공유 인터페이스, 테스트, 로컬 배포·실행기, 스냅샷 생성기**까지 이번 일정에 포함한다. PRD는 실행기를 2주차 설명에 배치했지만, 수요일의 anvil 완료 기준을 충족하려면 로컬 실행기는 미리 만들어야 한다.

테스트넷 10건 실측은 9/24, 약 800건 본 실행은 9/25가 PRD 일정이다. 수요일까지는 그 실행을 가능하게 하는 코드와 로컬 검증 결과를 준비한다. 과거 잔액으로 현재 가스 부족을 단정하지 않는다.

집중 개발 시간을 하루 7~10시간 정도 확보하는 경우의 계획이다. 오늘 규칙 정리와 팀 인계가 끝나야 성립하는 촘촘한 일정이며, 아래 시간은 견적이다.

## 4. 오늘 먼저 확인할 PRD 충돌과 빠진 규칙

단순 철자·타입 결정과 돈의 이동 규칙을 구분한다. 이름과 파일 구성은 민서가 초안을 정해 공유하고, 아래 경제 규칙은 PRD 작성자와 확인한다. 대기 중에도 Foundry 설정과 확정된 계산의 테스트는 진행할 수 있다.

### 시작 상태와 한도 — 오늘 결정

- **초기 LP 예치와 집중 한도 충돌 — D01 승인·초기 예치 구현.** PRD는 LP-01이 5,000을 예치하지만, 미상환 0일 때 개인 상한은 약 4,166.67이다. 9/20 민서가 지정 세 LP의 초기 5,000/3,000/2,000에만 개인 한도 예외를 승인했다. 풀 한도는 유지하며 초기 단계는 영구 종료된다. 9/21 완료 가드를 실제 advance 두 경로에 연결했다. 일반 예치는 아직 남아 있다.
- **발급사 초기 구성 승인·등록 구현.** 초기 HYBRID·AURA 등록 후 로컬 시간을 30일 진행해 시작하고, t9에 신규 세 곳을 등록한다. 계약은 실제 등록 시간으로 30일을 판단하며 날짜 수정 예외는 없다. Suspended 발급사의 한도 계산 인원수 포함 여부는 아직 합의가 필요하다.
- **역할 수는 14다.** PRD에 적힌 배포자 1 + 검증자 1 + 제출자 1 + 발급사 5 + LP 6 = 14이므로 0..13이 필요하다. 8..12는 LP 5개뿐이다. 기존 지갑 준비 상태를 먼저 확인하고 중복 생성하지 않는다.

### 토큰 이동과 회계 — 오늘 결정, 월요일 구현

- **수수료 지급 주체·시점 확인, 배분 확정 및 구현 완료.** Notion은 발급사가 선지급 실행 시 별도 잔액으로 납부하도록 명시한다. 9/21 민서는 PRD의 80/13.3/6.7%를 선택했다. 1,000당 3 수수료를 2.4/0.399/0.201로 기록한다. 상환에서 중복 청구하지 않는다.
- **발급사 서명·제출자 가스 부담으로 담보 입금 구현.** 담보 제공자는 발급사이며 이 역할은 PRD와 사용자 재확인으로 정해져 있다. MockUSDC Permit과 별도의 담보 작업 서명으로 입금까지 연결했다. 다음에는 상환·수수료 회계를 연결한다. permit만으로 특정 작업의 실행 의사가 증명되는 것은 아니다.
- **부분 상환·담보 회수·탈퇴·LP 출금 규칙은 무엇인가?** 담보 인출 후 미상환 보장, LP 지분의 원금/수수료/손실 배분, 대기 중 출금 금액의 취급을 정한다. 샘플의 LP 손실은 출금 후 감소하므로 “평생 누적손실”인지 “현재 LP에 남은 손실”인지 구분한다.

### 손실과 시나리오 — 오늘 쟁점 전달, 늦어도 월요일 종료 전 확정

- **회수 때 담보를 두 번 차감하면 안 된다.** t3에서 AURA 담보는 600 → 200으로 이미 400이 차감되어 있다. t3b의 최종 결과는 담보 부담 총 600, 풀 부담 총 1,200이다. 회수 수식에 현재 담보 200만 그대로 대입하면 기존 차감을 놓치므로, 기존 적용분과 최종 필요분을 어떻게 정산할지 명시한다.
- **상한의 “단일 사건” 범위가 필요하다.** 매입사 하나의 모든 과거 손실을 영구 합산할지, 사고별로 묶을지, 처리 순서와 상한 기준 예치금을 언제 고정할지 정한다. 회수 수식은 같은 매입사의 여러 포지션 대상인데 초안 함수는 refundKey 한 개이므로 API도 맞춘다.
- **출금의 스냅샷 시점이 다르다.** PRD 보조 설명은 t4에서 원금이 10,000 → 8,000으로 줄었다고 하지만, 표와 샘플은 t4=10,000, t5=8,000이다. t4 요청/부분 지급, t5 완료라는 해석이 맞는지 확인한다.
- **원장 반영 시점이 다르다.** 6장은 선지급 직후 잔액 복원, 10.6절·13장은 상환 확인 후 creditLedger라고 쓴다. 민재와 어떤 체인 이벤트가 DB 반영을 촉발하는지 맞춘다. t7의 재시도 증빙도 이에 의존한다.

### 인터페이스에서 함께 닫을 항목

- 9/21 구현: nonce 성공 시 소비, 거절 시 유지, deadline 정각 허용. PRD 사유는 거절 이벤트+false, 잘못된 nonce/입력·기술 실패는 revert.
- 어댑터는 receipt 성공뿐 아니라 Torna의 일치하는 AdvanceIssued 로그로 판정해야 한다. 규칙은 shared/abi/README.md에 기록했으며 실제 어댑터 통합은 남아 있다.
- markOverdue, 외부 운용 동결/회수 실패, LedgerCreditConfirmed에 대응하는 함수·권한. 현재 초안은 이벤트에 비해 함수가 부족하다.
- “1년 운영”, 영업일 T+5, 30일 램프업을 로컬과 테스트넷에서 각각 어떻게 표현할지. 로컬의 시간 이동 기능에만 의존하는 실행기는 그대로 테스트넷에 옮길 수 없다.
- 지표의 분모, 포지션 목록이 전체인지 표시용 일부인지, 스냅샷의 문자열 issuer 키와 온체인 address의 연결.
- 샘플의 YearlySummaryLoaded 등 표시용 이벤트를 실제 온체인 로그와 어떻게 구분할지. 실거래 번들에 존재하지 않는 로그나 tx hash를 만들어 넣지 않는다.

쟁점마다 “현재 문서 / 제안 / 팀 결정 / 영향을 받는 테스트” 한 줄을 남긴다. 샘플에 맞추려고 계약 로직이나 회계 수치를 조용히 바꾸지 않는다.

Foundry는 컴파일·테스트·배포에 쓰고, TypeScript 실행기는 PRD 권장대로 viem과 민재의 모듈을 사용한다. 배포와 초기 설정을 어느 쪽이 담당할지 하나로 정해 두 번 실행하지 않는다.

초기 실행기는 제출 계정별 순차 전송과 receipt 확인으로 단순하게 시작한다. 전송 오류 때는 기존 tx hash와 계정 nonce를 먼저 확인하고 새 승인을 무조건 발급하지 않는다. 입력, 송신자, nonce, tx hash, 결과, 가스 기록을 남겨 목·금 테스트넷 실행에 재사용한다.

|---|---|---|
| 일요일 종료 전 | 식별자·EIP-712·상태·단위·쟁점 목록 | 서진의 스키마 확인, 경제 규칙 결정 일정 |
| 월요일 종료 전 | 컴파일 ABI, 로컬 호출 예시, t0 결과 | 민재의 입력 fixture와 어댑터 import 경로 |
| 화요일 미니 통합 | 배포 주소, 서명 검증 결과, 스냅샷 | 실제 어댑터 서명·DB 반영, 프론트 로드 결과 |
| 수요일 오전 | 최종 실행 runId와 사용 키 목록 | 같은 회차의 라벨 덤프, t7 DB 재시도 증빙 |
| 수요일 종료 전 | 12시점 번들·테스트 결과·재실행 방법 | 번들 형식 수용 확인 |

라벨이나 실제 어댑터가 늦어져도 컨트랙트 단위 테스트는 계속한다. 다만 라벨이 없으면 최종 번들 검증은 미완료이며, 팀 의존 항목을 자신의 코드 완료와 분리해서 보고한다.

## 12. 실행 주체를 구현·테스트에 명시하기

- 발급사는 환불 payload에 오프체인 서명한다. 이 서명만으로 토큰이 움직이거나 가스가 발생하지 않는다.
- submitter는 advance/repay 트랜잭션을 서명하고 가스를 낸다. 성공 시 포지션·미상환·토큰/수수료 회계가 바뀌며, nonce·refundKey·허용 상태로 중복을 차단한다.
- verifier는 손실·회수 트랜잭션을 서명하고 가스를 낸다. 담보·준비금·LP 손실·포지션 상태가 바뀌며, 역할과 사건/포지션 처리 상태로 재처리를 막는다.
- LP는 자신의 예치·출금 트랜잭션을 서명하고 가스를 낸다. 잔액·지분·출금 요청 상태가 바뀌며, 잔여 청구액과 완료 상태를 확인한다.
- deployer는 배포·권한 설정을 수행한다. 로컬과 테스트넷의 네트워크를 구분하고, 테스트넷 배포 전 실제 chainId가 PRD의 10143인지 확인한다.

지급되는 USDC의 보유자와 가스를 내는 MON 계정은 다를 수 있다. 이 차이를 명시한 뒤 approve/transferFrom 흐름을 테스트한다.

## 13. 수요일 인수 체크리스트

- [ ] 공유 타입·ABI가 실제 계약과 일치하고 민재가 import한다.
- [ ] 규칙 충돌에 대한 결정과 테스트 기대값이 기록되어 있다.
- [ ] 정상·권한 실패·서명 변조·중복·만료·한도·토큰 전송 실패 테스트가 통과한다.
- [ ] 워터폴·상한·회수·LP 출금·부분 예치의 회계 검증이 통과한다.
- [ ] 실제 어댑터와 미니 통합 결과가 기록되어 있다.
- [ ] anvil에서 새 배포 후 12개 시점을 연속 실행한다.
- [ ] 상태/로그에서 생성한 12개 JSON과 manifest가 같은 runId를 가진다.
- [ ] 민재의 라벨 파일이 모든 사용 키를 포함하고 같은 runId를 가진다.
- [ ] 생성 번들 검증과 추가 지표 검증이 통과한다.
- [ ] 재실행 방법과 PR 인계 자료가 준비된다.

현재 사용 가능한 검증 명령은 아래와 같다. Foundry 명령은 프로젝트 구현 후 실행한다. 각 명령은 **저장소 루트에서** 실행하는 기준이다.

```bash
forge fmt --check --root packages/contracts
forge test --root packages/contracts -vv
pnpm verify:bundle shared/snapshots/run-local-20260923-01
```

JS 의존성 설치 전 샘플 형식만 확인할 때는 현재 환경에서 다음 명령을 사용할 수 있다. 이번 재검토에서 이 명령은 통과했다.

```bash
node --experimental-strip-types scripts/verify-bundle.ts shared/snapshots/sample
```

진행이 밀리면 기능별 브랜치/PR을 작게 유지하고, 라이브 모드·추가 인덱서·UI 지원 작업을 이번 개인 일정에 넣지 않는다. 핵심 회계나 12시점 검증을 빼고 완료로 표시하지 않는다. 화요일 밤에 핵심 시나리오가 실패하면 수요일 시간은 그 실패와 재실행에 배정한다.
