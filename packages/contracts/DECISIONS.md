# 구현 결정과 팀 확인 목록 — 9/21 갱신

담당: 민서(B). 오늘 구현한 기술 규칙과 아직 제품 합의가 필요한 항목을 구분한다.
이 문서는 팀에 보낼 검토 자료다. D01과 D02의 초기 구성·30일 경과 방식은 9/20 민서가 이 대화에서 승인했다. 9/21 D03 수수료 배분은 민서가 PRD 기준을 선택했다. 현재 선지급은 등록 인원수 그대로 계산하며, 중단 회사 제외로 다른 회사 한도를 늘리는 정책은 도입하지 않았다. 팀 전체의 동의·전송을 뜻하지 않는다. 아래 9/20 설명은 당시 구현 경계이며 최신 선지급 범위는 D03/9/21 절을 따른다.

## 구현한 기술 규칙

- 식별자는 원문 UTF-8 바이트를 keccak256으로 해시한다. Solidity `bytes(string)`과 viem `stringToHex`의 결과를 같은 고정 벡터로 검증한다.
- EIP-712 필드/순서는 interface-draft의 AdvanceRequest 그대로다. 이름 Torna, 버전 1, 실제 chainId와 계약 주소를 domain에 포함한다.
- TS 금액은 bigint 최소단위, 날짜는 Unix 초다. 입력 변환은 어댑터 담당이고 스냅샷 출력에서 표시 단위로 되돌린다.
- 상태 철자는 snapshot.ts와 동일하고 숫자 enum은 0부터 문서 순서다. 0값으로 존재 여부를 판단하지 않는다.
- 거절 코드는 PRD 번호를 유지한다. 잘못된 domain도 서명 검증 실패(3)로 처리하며 원인을 추측해 ChainMismatch(4)를 발행하지 않는다.
- MockUSDC는 6자리 ERC20 테스트 토큰이다. MINTER_ROLE만 민팅한다. OpenZeppelin ERC20Permit과 별도 담보 입금 요청 서명을 사용해 발급사는 오프체인 서명만 하고 제출자가 승인·입금을 실행한다. 담보 실제 수령 후 발급사별 잔액과 합계에 기록한다.
- 계산 라이브러리는 상태를 변경하지 않는다. 정수 나눗셈은 최소단위에서 내림하고 결과 표시 반올림은 별도로 한다.
- Limits는 7장 상세 식의 현재 미상환을 입력받는다. 초기 LP 예외는 승인된 D01에 따라 Torna의 별도 초기 예치 함수에만 구현했다. 선지급은 전체 등록 인원을 사용하며 중단/탈퇴 제외 정책은 미구현이다.
- Waterfall.absorb는 새로 확정한 전액 손실에만 적용한다. Waterfall.settleRecovery는
  동일 사건의 합산 원금·마진·기인식 손실을 받아 최종 부담과 차액만 계산한다.
  상태 변경·사건 묶음·회수금 입금은 Torna가 별도로 처리해야 한다.
- Foundry는 Shanghai EVM 타깃과 optimizer 1회 설정을 사용한다. 현재 `Torna` 런타임
  바이트코드가 EIP-170 24,576바이트 안에 들어오도록 한 설정이며, 테스트 전용
  `LiquidityGateHarness` 크기는 배포 대상 크기 판단에 포함하지 않는다.
- 손실 실행은 `VERIFIER_ROLE`만 호출한다. `openReview`는 만기 도래 후
  `Overdue` 이벤트와 `ReviewOpened`를 함께 기록하고 `Review`로 전환한다.
  `finalizeCoveredLoss`는 매입사별 누적 coverage를 LP 예치금의 20% cap과 비교해
  `CoveredLoss` 또는 `CapHeld`로 전환한다. `recordRecovery`는 검증자의 allowance에서
  회수금을 실제로 받아 같은 매입사 사건의 모든 포지션을 `RecoveryRecorded`로 바꾼다.
- 현재 구현은 한 사건(`acquirerHash`)에 한 발급사만 허용한다. 서로 다른 발급사를
  같은 사건으로 묶어야 하는 제품 요구가 생기면 `EventIssuerMismatch`를 없애고
  발급사별 담보 정산 정책을 먼저 합의해야 한다. 회수 기록 후 사건별 임시 집계는
  지워져 같은 매입사의 다음 사건을 새로 시작할 수 있지만, 이미 회수된 포지션은
  terminal 상태라 다시 회수할 수 없다.
- 회수 대상은 이벤트 전체를 하나의 회수율로 정산한다. PRD의 20% 마진이 모든
  포지션에 동일하므로 합산 `settleRecovery`가 PRD의 `Σ min(margin_i, un_i)`와
  일치한다. 포지션별 회수액을 허용하려면 별도 API와 합의가 필요하다.

## API 확정 시 함께 전달할 제안

### D01 확정 — 최초 유동성 구성에만 제한된 예외

상태: **9/20 민서 승인, 초기 예치 구현·검증 완료**. PRD 원문에 없는 예외를 이 대화에서 명시적으로 승인했다. 팀 전송은 아직 하지 않았다.

미상환 0에서 계산한 풀 상한은 16,666.666666 USDC, LP별 상한은 4,166.666666 USDC다. 기본 규칙으로 LP-01의 5,000 요청을 처리하면 833.333334가 거절되고 초기 총액은 9,166.666666이 된다. LP-02의 3,000과 LP-03의 2,000은 해당 금액 한도를 통과한다. 이 규칙의 25%는 실제 예치 잔액이 아닌 **풀 예치 한도**에 곱한다.

결정은 PRD의 초기 5,000/3,000/2,000과 총액 10,000을 유지하되, 처음 정한 LP 세 곳의 초기 자금 구성에만 LP별 집중 한도 예외를 두는 것이다.

- 초기 LP 주소와 주소별 예치액을 시작 전에 고정한다. 해당 주소가 정해진 초기 금액을 한 번씩 예치할 때만 예외를 적용한다.
- 예외는 LP별 집중 한도에만 적용한다. 풀 총예치 한도와 실제 토큰 수령 검사는 그대로 적용한다.
- 총 10,000 구성이 끝나야 선지급을 시작하고, 초기 구성 단계는 자동 종료된다. 관리자도 다시 열 수 없다.
- 다른 주소, 초기 금액 초과, 같은 초기 예치의 재실행에는 예외를 적용하지 않는다.
- 운영 시작 후 추가 예치는 초기 LP도 동일한 한도 식을 적용한다. LP-01이 여전히 개인 상한을 초과하면 추가 예치 가능액은 0이다. 기존 예치의 강제 출금은 새로 도입하지 않는다.
- LP는 자신의 approve·초기 예치 트랜잭션을 서명하고 가스를 낸다. 계약은 실제 수령 토큰과 LP 권리를 기록하며 주소별 초기 예치 완료 여부와 단계 종료 상태로 중복을 막는다.

단점은 운영 중 한도보다 큰 초기 집중을 명시적으로 허용한다는 것이다. 초기 LP 금액/구성을 바꾸는 대안 대신 이 예외를 선택했다.

구현 API: 관리자가 `configureInitialLiquidity(address[3])`로 주소를 한 번 고정한다. LP는 `depositInitialLiquidity(uint256)`를 직접 호출한다. 원금은 `lpPrincipal`/`totalLpPrincipal`, 상태는 `initialLiquidityConfigured`/`initialLiquidityComplete`/`initialLiquidityDeposited`로 조회한다. 설정 후 주소 교체도 불가하므로 설정 전 주소 확인이 필수다. 추가 설정 이벤트는 `InitialLiquidityConfigured`, `InitialLiquidityCompleted`이며 기존 `LiquidityDeposited`도 실제 발행한다.

추가 테스트 17개: 권한·주소/금액 고정, 중복/초과/다른 주소 차단, 전송 실패·수령액 부족 시 토큰·원금·완료 상태 롤백 및 재시도, 재진입 차단, 예치 순서 독립성, 직접 송금의 원금/완료 불인정, 종료 후 재개 금지, 초기 원금에 대한 일반 한도 계산.

구현 경계: `whenLiquidityReady` 가드는 테스트 하네스로 검증했다. **실제 advance 함수는 아직 없으며 향후 반드시 이 가드를 연결해야 한다.** 일반 예치 실행도 미구현이라, 운영 중 한도는 실제 초기 원금을 기존 Limits 식에 대입해 검증했다. LP 원금 기록만 있으며 NAV/지분·출금 회계는 다음 작업이다. 출금 경로가 없으므로 실제 자금을 넣지 않고 로컬 테스트 토큰만 사용한다.

### D02 부분 확정 — 초기 회사 두 곳과 신규 회사 세 곳

상태: **9/20 민서 승인, 등록·시간 기반 램프업 구현·검증 완료**. 승인 범위는 초기 HYBRID·AURA를 30일 지난 기존 회사로 시작하고, NOVA·MERIDIAN·KITE는 시점 9에 신규 등록하는 것이다. 거래 중단된 회사(Suspended)를 한도 계산의 발급사 수에 포함할지는 아직 결정하지 않았다.

- PRD에 이미 있는 규칙: 등록 후 첫 30일은 담보 기반 한도에 50%, 정확히 30일이 되는 시점부터 100%를 적용한다. 최종 한도는 풀 집중 한도와 비교해 더 작은 값이다.
- 관리자만 `registerIssuer(address, bytes32, string)`로 등록한다. 등록 시간은 호출 시점의 블록 시간이며 과거 날짜 입력·수정·중복 등록은 허용하지 않는다. 잘못된 주소·빈 이름·빈 매입사 해시도 차단한다.
- `issuerRegistrationOf`는 등록 정보만 조회한다. 별도 exists 값으로 존재를 확인하며, 등록 사실을 Active 상태나 담보 보유로 간주하지 않는다. `isIssuerRamping`은 30일 경과 여부를 조회한다. 미등록 주소는 두 조회 모두 거절한다.
- `previewIssuerLimit`은 등록 시간을 사용하되 담보·풀 가능액·발급사 수는 입력으로 받는 **계산 확인용 함수**다. 실제 대출 가능액 조회나 선지급 승인이 아니다. 실제 advance에서는 저장된 회계와 발급사 상태를 사용해야 한다.
- 로컬 테스트: 초기 두 회사 등록 → 테스트 시간 30일 진행 → 데모 시작 조건 확인 → 나중에 세 회사 신규 등록. 실계약에 특정 회사 예외나 시간 조작 함수를 넣지 않았다. 테스트넷 시간 표현은 D10에서 별도 결정한다.
- 추가 테스트 12개: 관리자 권한, 등록 이벤트/정보, 잘못된 입력, 중복 등록 시 시간/정보 유지, 미등록 조회 차단, 등록 직후·30일 1초 전·정각·직후, 풀 집중 한도 유지, 0담보/0풀 한도, 0시각 등록, 초기 2곳/추가 3곳 구성, 여러 등록 시간·경과 시간의 퍼즈 검증.

남은 일: 중단/탈퇴 발급사 수 계산 정책, 운영상태, 선지급 검사 연결, anvil 전체 시나리오 실행기. 담보 입금은 아래 D04에서 구현했다. 등록 순서 테스트 통과를 전체 12시점 실행 완료로 표시하지 않는다.

### D04 진행 — 발급사 서명, 제출자 가스 부담, 토큰 Permit 승인

사용자가 PRD의 역할을 재확인하고 서명 기반 승인 기능 구현을 요청했다. **담보 제공자가 발급사라는 점과 제출자가 가스를 낸다는 점을 미정으로 다루지 않는다.** 부족했던 것은 가스 없이 발급사 토큰 사용을 승인하는 구현 방법이다.

- MockUSDC에 OpenZeppelin 5.4.0 `ERC20Permit`을 사용했다. 서명 검증·만료·nonce 처리를 직접 새로 만들지 않았다.
- 발급사는 `owner=자신`, `spender=Torna 계약`, `value=필요 금액`, 토큰의 현재 `nonce`, `deadline`에 서명한다. 제출자가 `permit` 거래를 보낸다. 발급사에게 approve 거래나 가스 잔액이 필요하지 않다.
- 승인받는 것은 제출자 지갑이 아니라 Torna다. 표준 permit은 누구나 전달할 수 있지만 전달자에게 토큰 사용 권한을 주지 않는다.
- 토큰 서명 domain은 `Torna Mock USDC`, 버전 `1`, 실제 chainId와 MockUSDC 주소다. 선지급의 Torna domain과 혼용하지 않는다. 토큰 nonce와 향후 advance nonce는 별개다.
- 서명은 한 번만 사용 가능하다. 성공 시 승인액을 설정하고 nonce를 증가시킨다. 잘못된 서명·만료·재사용 시 revert하고 nonce와 승인액을 유지한다. deadline 정각은 허용한다.
- **deadline은 서명을 제출할 수 있는 기한이며, 이미 등록된 승인액의 만료 시간이 아니다.** 새 서명으로 value=0을 승인하면 해당 spender의 승인을 취소할 수 있다. 테스트에서도 이 경계를 검증했다.
- 공유 파일 `shared/abi/permit.ts`와 공개 해시 벡터 `fixtures/permit.json`을 추가했다. 실제 키나 유효한 승인 서명을 기록하지 않는다.

토큰 승인에 이어 사용자가 담보 입금 구현을 요청해 아래까지 연결했다. 수수료 결제·상환은 아직 구현하지 않았다. 외부 실제 USDC나 스마트 계약 지갑 지원을 주장하지 않는다.

#### 담보 입금 구현

- 발급사는 Permit 외에 `CollateralDepositRequest(issuer, amount, nonce, deadline)`에도 서명한다. 토큰 승인만으로 제출자가 임의로 담보를 넣을 수 없게 하는 작업별 승인이다. 두 서명 모두 오프체인이라 발급사 가스는 필요하지 않다.
- 입금 서명은 Torna domain을 사용하며 `collateralDepositNonces(issuer)`로 중복 실행을 차단한다. 토큰 Permit nonce 및 향후 advance nonce와 별개다. deadline 정각은 허용하고 이후에는 거절한다.
- `depositCollateral(request, signature)`는 기존 토큰 승인액을 사용한다. `depositCollateralWithPermit(request, signature, permitSignature)`는 승인과 입금을 한 거래에서 처리한다. 두 함수 모두 SUBMITTER_ROLE만 호출할 수 있다.
- 기존 초안의 `depositCollateral(address,uint256)`를 위 서명 포함 API로 구체화했다. 입금 대상은 등록된 발급사이며, 금액은 0보다 커야 한다. 서명한 발급사의 지갑에서만 토큰을 가져오고 같은 발급사의 담보로만 기록한다. 다른 수취인을 입력할 수 없다.
- 실제 수령액이 요청 금액과 같은지 확인한 후 `collateralOf(issuer)`와 `totalCollateral`을 늘리고 `CollateralDeposited`를 발행한다. LP 원금과 별도로 기록하며, 담보·직접 송금으로 LP 초기 구성 완료 조건을 채우지 않는다.
- 이미 다른 사람이 permit을 등록했더라도 유효한 담보 입금 요청과 충분한 승인액이 있으면 진행한다. permit 실패를 무시해도 입금 서명·만료·nonce·승인액 검사를 건너뛰지는 않는다.
- 전송 실패·수령액 부족 시 같은 거래의 토큰 이동·담보 기록·입금 nonce·신규 permit 처리가 모두 원복된다. 별도 이전 거래에서 등록된 permit은 그대로 유지된다. 재진입도 차단한다.
- 공유 파일 `shared/abi/collateral.ts`에 입금 서명 타입과 실제 함수 ABI를 추가했다. `fixtures/collateral-deposit.json` 해시 벡터와 컴파일 ABI를 Solidity/TypeScript 양쪽에서 검증한다.
- 담보 관련 신규 Solidity 테스트 24개(동작 23 + 벡터 1), TypeScript 테스트 5개를 추가했다. 발급사 가스 잔액 0, 권한/위조/만료/재사용, 선제 permit 제출, 실패 후 재시도, 다중 발급사별 기록, 추가 입금 누적, LP 회계 분리를 검증했다.

구현 경계: 담보 인출·손실 차감·운영상태 자동 전환·저장된 담보에 연결된 선지급 검사는 아직 없다. 기존 previewIssuerLimit은 예시 입력 계산용으로 유지한다. 출금 경로가 없으므로 실제 자금은 입금하지 않으며, 이번 검증은 로컬 Foundry 테스트다. 테스트넷 배포·실지갑 거래·12시점 번들 생성은 수행하지 않았다.

## D03 / 9/21 — 선지급 실행과 수수료 회계

### 문서에서 확인한 것과 사용자 결정

- [Notion 6. 유동성·위험·수익 구조](https://app.notion.com/p/3e1a11e2bcf7803abe17e5a3fb33cdec): 발급사가 선지급 성공 시 별도 잔액으로 이용 수수료를 납부한다. 원금 전액 지급, 사용자 수수료 0, 거절 요청 이용 수수료 0, 상환 시 원금만 납부. 가스비는 별도 제출자 부담.
- Notion 예시는 3을 2.40/0.40/0.20으로 나누지만 PRD는 80/13.3/6.7%다. 민서가 **“PRD기준으로 가”**라고 선택했다. 따라서 1,000당 3 수수료를 LP 2.400000, 준비금 0.399000, 프로토콜 0.201000으로 기록한다.
- 정수 정밀도 처리: 전체 수수료·LP·준비금 몫은 최소단위에서 내리고, 남은 값은 프로토콜 몫으로 기록해 합계를 보존한다. 별도 최저 수수료는 도입하지 않았다.
- 기존 샘플을 계약 결과인 것처럼 고치지 않았다. 향후 실제 실행 번들은 이 정확한 비율로 생성·검증해야 하며 기존 샘플과의 차이를 숨기지 않는다.

### 구현한 실행 규칙

- `advance(request, signature)`와 `advanceWithPermit(request, signature, permitSignature)` 추가. 제출자 역할·초기 LP 구성 완료가 필수다. 원래 AdvanceRequest 서명 필드/domain은 변경하지 않았다.
- 수수료 Permit의 value는 수수료만이다. 유효한 선지급 작업 서명도 별도로 필요하다. 미리 전달된 Permit 때문에 combined 호출이 막히지 않으며, Permit 실패를 허용해도 충분한 실제 allowance가 없으면 전체 거래가 취소된다.
- 선지급 전 키 중복, 등록, deadline, 서명, 순차 nonce, 양수 금액/비어 있지 않은 키/미래 만기, 등록 매입사 일치, 상태, 발급사·매입사 한도와 풀 현금을 검사한다. maturity의 영업일 계산은 어댑터 책임이다.
- PRD 사유는 `AdvanceRejected`+false로 끝나며 nonce/Permit/수수료를 소비하지 않는다. code 4는 서명만으로 구별 불가능해 쓰지 않는다. 기술/잘못된 입력 오류는 revert한다. 어댑터는 Torna 주소와 요청에 일치하는 AdvanceIssued 로그를 확인해야 한다.
- 수수료 수령 → 포지션/미상환/수수료/성공건수/nonce 기록 → 원금 전액 지급. 중간 실패 시 모든 변경과 이번 거래의 Permit까지 롤백한다. 선행 거래의 Permit은 그대로다.
- 포지션은 exists, 발급사, 매입사, 원금, 수수료, 20% 손실 부담액, 80% 보장액, 만기, termsVersion=1, Advanced 상태를 저장한다. 담보를 건별 잠그거나 차감하지 않는다.
- `issuerLimit`은 실제 담보·LP 회계·등록 수·등록 시간을 사용한다. 등록 수는 담보 0인 곳도 포함하며, 중단을 이유로 다른 회사 한도를 확대하지 않는 보수적인 현재 구현이다. 제외/제명 정책을 승인된 것으로 기록하지 않는다.
- `issuerStateOf`는 현재 잔액에서 상태를 계산한다. 담보 0은 Suspended, 15% 필요 마진 부족은 MarginCall이다. 행정적 중단/탈퇴와 손실 처리 상태 전이는 아직 없다.
- 현재 풀 가능액은 LP 원금+누적 LP 수수료, 사용 가능 현금은 여기서 미상환을 뺀 값이다. 담보·준비금·프로토콜 몫·직접 송금은 LP 가용액에 넣지 않는다. 실제 잔액이 이 장부를 뒷받침하는지도 검사한다.

### 구현 경계와 인계

- 선지급과 `Advanced` 포지션의 전액 원금 상환은 완료했고, 준비금 500 시드 입금은 관리자 전용 1회성 `seedReserve`로 구현했다. 부분 상환·LP별 수익 분배/출금·일반 예치·외부 운용·손실/회수·행정 상태 변경은 미구현이다. 이 기능들을 추가할 때 풀 회계/상태 계산도 확장해야 한다.
- PRD의 시간 기반 30일 규칙을 유지했다. Notion의 “정상 상환 이력 후 해제”라는 추가 표현을 별도 조건으로 도입하지 않았다. 기존 민서 승인 D02와 PRD를 기준으로 한다.
- `shared/abi/advance.ts`는 호출/조회 타입, `shared/abi/Torna.json`은 컴파일 결과에서 생성한 전체 ABI다. `export:abi`로 재생성하며 테스트로 컴파일 ABI와 비교한다. 선언된 미래 이벤트가 있어도 해당 함수까지 구현됐다는 뜻은 아니다.
- 어댑터 본체·DB 반영은 수정하지 않았다. 실제 어댑터 연결, 테스트넷 배포, 새 12시점 번들 생성은 아직 수행하지 않았다. 로컬 가짜 계정·토큰만 사용한다.

## D05 / 9/22 — 정상 경로의 전액 원금 상환

- PRD 6·12장의 정상 경로와 “상환 시 원금만 납부” 규칙만 구현했다. 부분 상환 정책은 여전히 미결정이며 지원한다고 기록하지 않는다.
- 발급사는 `RepaymentRequest(refundKey, issuer, amount, nonce, deadline)`와 선택적인 MockUSDC Permit을 오프체인 서명한다. 제출자가 `repay` 또는 `repayWithPermit`을 호출하고 가스를 낸다.
- 상환 금액은 저장된 포지션 원금과 정확히 같아야 한다. 현재 허용 상태는 `Advanced`뿐이며 성공 시 `Repaid`로 바뀐다. t5의 `Overdue`/`Review` 이후 상환 전이는 별도 합의가 필요하다.
- 성공 시 발급사·매입사·전체 미상환만 감소한다. 수수료를 다시 받지 않고, 누적 선지급 건수·금액·담보·수수료 장부는 바꾸지 않는다.
- `repaymentNonces`와 포지션 상태가 재실행을 막는다. 토큰 Permit nonce, 담보 입금 nonce, 선지급 nonce와 혼용하지 않는다.
- 토큰 수령액과 발급사 차감액을 모두 원금과 대조한다. 부족 allowance, 전송 실패/부족 수령, 재진입, 장부보다 부족한 실제 자산은 전체 거래를 되돌린다.
- `shared/abi/repayment.ts`, 공개 해시 벡터, 컴파일 ABI와 Solidity/TypeScript 교차 검증을 추가했다. 실제 어댑터 연결과 테스트넷 거래는 아직 검증하지 않았다.
